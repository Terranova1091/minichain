# minichain

Учебный блокчейн на Rust: аккаунтная модель, доказательство работы (PoW), дерево Меркла, автоматическая подстройка сложности, хранение цепи в JSON и консольный интерфейс. Проект написан для понимания устройства блокчейна «изнутри»: каждое проектное решение зафиксировано в ADR (см. `docs/adr/`).

> **Важно.** Это учебный проект, а не боевая система. У транзакций нет подписей, нет сети и нет выбора между конкурирующими цепями (см. [Ограничения](#ограничения)). Не используйте его для хранения чего-либо ценного.

## Возможности

- Блоки с заголовком фиксированного размера (96 байт) и хэшем `SHA-256(SHA-256(header))`.
- Дерево Меркла с доменным разделением листьев и узлов, доказательства включения (`merkle_proof` / `verify_proof`).
- PoW: хэш заголовка должен иметь не менее `bits` ведущих нулевых бит.
- Пересчёт сложности каждые 10 блоков (целевое время блока 10 секунд).
- Аккаунтная модель: балансы и `nonce` на адрес, награда майнеру (coinbase), атомарное применение блока.
- Полная валидация цепи: 9 проверок на блок, включая медианное время и допуск на будущее.
- Хранение: один JSON-файл, атомарная запись, полная перепроверка при загрузке.
- Очередь неподтверждённых транзакций (mempool) в отдельном файле.
- CLI: `init`, `send`, `mine`, `show`, `verify`.

## Быстрый старт

Нужен Rust (stable). Сборка и запуск:

```
cargo build --release
```

Режим `--release` важен: майнинг в debug-сборке в десятки раз медленнее.

```
# создать цепь со сложностью 16 бит (генезис-блок)
cargo run --release -- --data-dir ./data init --bits 16

# намайнить блок: награда достаётся alice
cargo run --release -- --data-dir ./data mine --to alice

# поставить перевод в очередь
cargo run --release -- --data-dir ./data send --from alice --to bob --amount 10

# намайнить блок с этим переводом
cargo run --release -- --data-dir ./data mine --to alice

# состояние цепи: высота, вершина, сложность, очередь, балансы
cargo run --release -- --data-dir ./data show

# один блок целиком
cargo run --release -- --data-dir ./data show --height 2

# полная перепроверка файла цепи
cargo run --release -- --data-dir ./data verify
```

Пока alice ничего не намайнила, у неё нет монет, поэтому `send` идёт после первого `mine`.

## Команды

| Команда | Что делает |
|---|---|
| `init --bits N` | Создаёт `chain.json` с детерминированным генезис-блоком. Отказывает, если файл уже есть. |
| `send --from A --to B --amount X` | Проверяет перевод и ставит его в очередь (`pending.json`). `nonce` вычисляется автоматически. |
| `mine --to ADDR` | Собирает блок из награды и применимых транзакций очереди, майнит его, добавляет в цепь и сохраняет. |
| `show [--height H]` | Без аргумента: сводка и балансы. С `--height`: заголовок и транзакции блока. |
| `verify` | Загружает файл цепи с полной перепроверкой; при ошибке сообщает высоту блока. |

Общий параметр `--data-dir` (по умолчанию текущий каталог) задаёт каталог с файлами `chain.json` и `pending.json`. Код возврата `0` при успехе, `1` при ошибке (сообщение в stderr).

## Как это устроено

### Блок

Заголовок состоит из 96 байт (все числа big-endian):

| Поле | Размер |
|---|---|
| `version` (u32) | 4 |
| `height` (u64) | 8 |
| `prev_hash` | 32 |
| `merkle_root` | 32 |
| `timestamp` (u64, секунды) | 8 |
| `bits` (u32) | 4 |
| `nonce` (u64) | 8 |

Идентификатор блока это `SHA-256(SHA-256(заголовок))`. Транзакции в заголовок не входят: они связаны с ним через `merkle_root`.

### Дерево Меркла

Лист хэшируется с префиксом `0x00`, внутренний узел с префиксом `0x01` (доменное разделение: лист не может сойти за узел). Если на уровне нечётное число узлов, последний поднимается на следующий уровень без дублирования. Это исключает класс коллизий, при которых разные списки транзакций дают один корень (ADR 0001).

### Доказательство работы

Блок валиден, если хэш заголовка имеет не менее `bits` ведущих нулевых бит. Каждый дополнительный бит вдвое уменьшает долю подходящих хэшей, то есть вдвое увеличивает ожидаемое число попыток: в среднем нужно `2^bits` значений `nonce` (ADR 0002).

### Сложность

Каждые `RETARGET_INTERVAL = 10` блоков сложность пересчитывается по фактическому времени окна против целевого (`TARGET_BLOCK_TIME_SECS = 10`). За один пересчёт `bits` меняется не более чем на 2 и всегда остаётся в диапазоне `[1, 255]`. Первое окно начинается с блока 1, а не с генезиса: метка времени генезиса фиксирована и далеко в прошлом (ADR 0003, ADR 0006 п. 7).

### Состояние

`State` хранит для каждого адреса баланс и `next_nonce`. Транзакция `from → to` списывает с отправителя и зачисляет получателю; её `nonce` должен совпадать с `next_nonce` отправителя (защита от повторного применения). Первая транзакция блока это награда (coinbase): у неё пустой `from`, фиксированная сумма и `nonce`, равный высоте блока. Арифметика везде с проверкой переполнения, блок применяется атомарно (на копии состояния, затем подмена) (ADR 0005).

### Валидация блока

Блок принимается, только если выполнены все проверки по порядку: версия, высота, `prev_hash`, ожидаемые `bits`, корень Меркла, PoW, метка времени строго больше медианы последних 11 блоков, метка не дальше 120 секунд в будущее от «сейчас», применимость транзакций к состоянию. Текущее время передаётся параметром, а не читается внутри библиотеки (ADR 0006).

### Хранение

Цепь записывается одним JSON-документом: `{"format_version": 1, "blocks": [...]}`. Хэши хранятся hex-строками, неизвестные поля запрещены. Состояние в файле **не хранится**: при загрузке цепь воспроизводится блок за блоком с полной валидацией, поэтому любая правка файла обнаруживается и указывает на высоту сбойного блока. Запись атомарная: временный файл, `sync_all`, `rename` (ADR 0007).

### Очередь транзакций

`send` добавляет транзакции в `pending.json`. Новая транзакция проверяется против состояния, *спроецированного* с учётом уже стоящих в очереди, поэтому очередь не принимает того, что блок отвергнет. Очередь считается кэшем намерений, а не истиной: после загрузки она перепроверяется (`revalidate`) и устаревшие записи отбрасываются. Благодаря этому сбой между сохранением цепи и очереди ничего не ломает.


## Время майнинга

Ожидаемое число попыток равно `2^bits`; фактическое время случайно (экспоненциальное распределение), поэтому отдельный блок может занять и вдвое больше, и в разы меньше среднего. Значения ниже замерены в release-сборке: среднее по 20 блокам на каждую сложность.

| `bits` | Ожидаемых попыток | Среднее время |
|---|---|---|
| 12 | 4 096 | _пока измерения не проводились_ |
| 16 | 65 536 | _пока измерения не проводились_ |
| 20 | 1 048 576 | _пока измерения не проводились_ |
| 24 | 16 777 216 | _пока измерения не проводились_ |

Как замерить: `init --bits N` во временном каталоге, затем 20 раз `mine --to x` под `time` (или `Measure-Command` в PowerShell), среднее делится на 20. Отношение времён соседних строк должно быть близко к 16 (4 бита = ×16).

## Ограничения

Это сознательные упрощения учебной версии (J1), а не ошибки.

- **Нет подписей.** Адрес это просто строка, транзакции не аутентифицируются: любой может отправить перевод «от имени» любого адреса. Это главное отличие от реальных систем; криптографическая часть выходит за рамки J1.
- **Нет сети.** Один процесс, одна цепь, обмена блоками между узлами нет. Нет выбора между конкурирующими цепями и откатов.
- **Хвост файла не защищён.** Файл цепи не хранит итоговую высоту или хэш, поэтому обрезанный хвост неотличим от более короткой валидной цепи (зафиксировано тестом и в ADR 0007).
- **Нет блокировки файлов.** Одновременный запуск двух команд над одним каталогом данных может привести к потере одной из записей.
- **Время берётся из локальных часов.** Доверие к ним ограничено допуском 120 секунд и медианным временем.
- **Размер блока и число транзакций не ограничены.**
- **JSON-хранилище** читается целиком в память: подходит для тысяч блоков, не для миллионов.
