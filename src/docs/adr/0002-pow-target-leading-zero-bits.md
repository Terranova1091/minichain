# ADR 0002: Цель Proof-of-Work задаётся числом ведущих нулевых бит

- Статус: принято
- Дата: 2026-11-03

## Контекст

Для добавления блока в цепочку нужно доказать, что затрачена вычислительная работа
(Proof-of-Work). Майнер перебирает поле `nonce` в заголовке блока, пока хэш заголовка
не удовлетворит заданной сложности. Узел при получении блока проверяет это одним
вычислением хэша.

Поле `bits: u32` в заголовке (96 байт: version, height, prev_hash, merkle_root,
timestamp, bits, nonce) должно определять сложность. Нужно выбрать:

1. что означает значение `bits`;
2. как считается хэш заголовка и как он сравнивается с целью;
3. что делать с граничными значениями `bits`.

## Решение

### 1. Семантика `bits`

`bits` — требуемое число **ведущих нулевых бит** хэша заголовка.

Хэш удовлетворяет цели, если `leading_zero_bits(hash) >= bits`.

Ожидаемое число попыток майнера равно `2^bits`. Каждый дополнительный бит удваивает
сложность. Для справки: `bits = 12` — около 4 тыс. попыток, `bits = 20` — около 1 млн,
`bits = 24` — около 16 млн.

### 2. Хэш заголовка

`header_hash = sha256d(header.to_bytes())`, где `to_bytes()` — каноническая
кодировка заголовка в 96 байт (big-endian для всех целых полей).

Хэш всегда считается узлом самостоятельно и никогда не берётся из полученных данных.

Биты считаются от старшего бита первого байта массива `[u8; 32]` в порядке хранения.
Разворота байт, как в Bitcoin при отображении хэша, не делаем: строка hex
соответствует байтам в том порядке, в котором считаются нули.

### 3. Граничные значения

Допустимый максимум `MAX_BITS = 256` (длина хэша в битах).

| `bits`          | Поведение `meets_target`                                  |
|-----------------|-----------------------------------------------------------|
| `0`             | всегда `true` (любому хэшу достаточно нуля нулевых бит)   |
| `1..=256`       | `leading_zero_bits(hash) >= bits`                         |
| `> 256`         | всегда `false` (такую цель выполнить невозможно)          |

`meets_target` возвращает `bool` и не паникует ни при каких входных данных.

Значение `bits = 256` формально достижимо только хэшем из одних нулей и на практике
недостижимо, но корректно обрабатывается.

### 4. Защита от слабой цели в заголовке

Значение `bits` приходит в заголовке блока от майнера, поэтому `meets_target` само по
себе не защищает от блока с `bits = 0`. Валидатор цепочки обязан отдельно проверять,
что `header.bits` **равно ожидаемому значению**, вычисленному по правилам корректировки
сложности (retarget) для данной высоты. Блок с другим `bits` отвергается независимо от
того, выполнен ли PoW. Правила retarget и значение для genesis описываются в отдельном ADR.

## Последствия

Плюсы:
- простая реализация и проверка: счёт нулевых бит, без арифметики над 256-битными числами;
- легко рассуждать о сложности: `2^bits` попыток, удобно для таблицы времени майнинга
  в README (bits 12/16/20/24);
- нет паник на граничных значениях.

Минусы:
- сложность меняется только ступенями в 2 раза, нельзя подстроить её плавно
  (в Bitcoin цель — полное 256-битное число в формате compact target);
- корректировка сложности должна работать с целыми шагами `bits`
  (например, ±1 бит за один период), это ограничение для ADR о retarget;
- формат несовместим с Bitcoin. Для учебного проекта принято сознательно.

## Рассмотренные альтернативы

1. **Compact target как в Bitcoin** (мантисса и экспонента, сравнение хэша как
   256-битного числа). Даёт плавную корректировку, но заметно сложнее в реализации и
   тестировании и не нужен для целей проекта J1.
2. **`bits = 0` и `bits > 256` как ошибка.** Требует `Result` в самой проверке цели.
   Отвергнуто: проверка должна быть простым предикатом, а недопустимые значения
   отсекаются валидацией блока (см. п. 4).
3. **Считать нули в hex-строке.** Хуже по производительности и зависит от формата
   отображения. Отвергнуто.

## Тесты, фиксирующие решение

- `leading_zero_bits`: все нули → 256; `0x80…` → 0; `0x01…` → 7; `00 00 10…` → 19; `00 ff…` → 8.
- Граница: хэш с ровно 12 нулевыми битами проходит для `bits = 12` и не проходит для `13`.
- `meets_target(h, 0) == true` для любого `h`; `meets_target(h, 257) == false` для любого `h`;
  `meets_target(zero_hash, 256) == true`.
- Изменение каждого поля заголовка меняет `header_hash`.
