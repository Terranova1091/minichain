# ADR 0005: Состояние цепи: аккаунты с балансом и nonce, правила применения транзакций и блоков

- Статус: принято
- Дата: 2026-11-07
- Связано: ADR 0001 (Merkle), ADR 0004 (генезис и coinbase)

## Контекст

Блок сам по себе только контейнер с транзакциями. Чтобы отвергать невозможные переводы
(нет денег, повтор, неверный порядок), нужно состояние цепи: у кого сколько средств
после всех блоков от генезиса. Состояние не хранится в блоках, а **вычисляется
проигрыванием** блоков от пустого состояния. Любой узел, проиграв одну и ту же цепь,
обязан получить одно и то же состояние, поэтому правила применения являются частью
консенсуса.

ТЗ описывает состояние как `BTreeMap<String, u64>` (балансы) и требует отвергать
перевод без достаточного баланса или с неверным nonce. Проверка nonce требует
хранить счётчик для каждого отправителя, а одного баланса для этого недостаточно.

Транзакции в J1 не подписаны (подписи появятся в J2 и J4). Защита от повторного
воспроизведения (replay) обеспечивается только nonce.

## Решение

### 1. Структура состояния

```rust
State   { accounts: BTreeMap<String, Account> }
Account { balance: u64, next_nonce: u64 }
```

Это отклонение от ТЗ: вместо `BTreeMap<String, u64>` хранится аккаунт с двумя полями.
Раздел ТЗ о состоянии обновляется соответственно.

- `BTreeMap`, а не `HashMap`: порядок обхода детерминирован (важно для отладки,
  сериализации и возможного хэша состояния).
- Аккаунт создаётся лениво, при первом получении средств: `balance = amount`,
  `next_nonce = 0`.
- Для неизвестного адреса `balance() = 0`, `next_nonce() = 0`. Отправителя, которого
  нет в состоянии, транзакция не может использовать (см. п. 2).

### 2. Правила обычной транзакции (`from` не пуст)

Все проверки выполняются **до** изменения состояния. Если хоть одна не прошла,
состояние остаётся прежним.

| Правило                                                    | Ошибка                                  |
|------------------------------------------------------------|-----------------------------------------|
| `amount > 0`                                               | `ZeroAmount`                            |
| `from != to`                                               | `SelfTransfer`                          |
| отправитель есть в состоянии                               | `UnknownSender`                         |
| `tx.nonce == sender.next_nonce`                            | `NonceMismatch { expected, got }`       |
| `sender.balance >= amount`                                 | `InsufficientBalance { balance, amount }` |
| `recipient.balance + amount` не переполняет `u64`          | `Overflow`                              |
| `sender.next_nonce + 1` не переполняет `u64`               | `Overflow`                              |

После успешных проверок:

- баланс отправителя уменьшается на `amount` (`checked_sub`);
- баланс получателя увеличивается на `amount` (`checked_add`), аккаунт создаётся при необходимости;
- `sender.next_nonce` увеличивается на 1 (`checked_add`).

Запрет `amount = 0` и `from == to` принят сознательно. Такие транзакции ничего не
переводят, но сдвигают nonce и занимают место в блоке, а их допустимость относится к
консенсусным правилам: узлы с разными правилами разошлись бы в оценке блока.

### 3. Правила coinbase (`from` пуст)

- `amount == COINBASE_REWARD` (50);
- `to` не пуст;
- `nonce == height` блока: у coinbase разных блоков разные байты, а значит и разные
  хэши листьев;
- получателю начисляется награда (`checked_add`);
- `next_nonce` получателя **не меняется**: coinbase отправлена не от его аккаунта.

Транзакция с пустым `from` по определению является coinbase, поэтому «обычная
транзакция с пустым отправителем» невозможна.

### 4. Правила блока

- блок содержит минимум одну транзакцию (иначе `EmptyBlock`);
- первая транзакция coinbase, остальные нет. Ровно одна coinbase:
  отсутствие в начале даёт `FirstTransactionNotCoinbase`, вторая и последующие с пустым
  `from` дают `UnexpectedCoinbase`;
- coinbase проверяется по п. 3 с `height` блока, остальные по п. 2;
- транзакции применяются **строго по порядку**. Отправитель может потратить средства,
  полученные ранее в том же блоке, а его nonce растёт внутри блока: транзакции с
  nonce 0 и 1 проходят подряд, 0 и 0 нет;
- **атомарность**: применение блока либо проходит целиком, либо состояние не меняется.
  Реализация: клонировать состояние, применять транзакции к копии, при успехе заменить
  исходное состояние копией.

### 5. Арифметика

Все операции над балансами и nonce используют `checked_add` и `checked_sub` и возвращают
ошибку при переполнении. Операторы `+` и `-` и `unwrap` в этом коде не используются.

### 6. Ошибки

`StateError` содержит варианты: `ZeroAmount`, `SelfTransfer`, `UnknownSender`,
`NonceMismatch { expected, got }`, `InsufficientBalance { balance, amount }`, `Overflow`,
`EmptyBlock`, `FirstTransactionNotCoinbase`, `UnexpectedCoinbase`, `InvalidCoinbase`.
Derive: `Debug, Clone, PartialEq, Eq`.

## Последствия

Плюсы:
- защита от replay и упорядочивание транзакций одного отправителя без подписей;
- правила однозначны и проверяются тестами, состояние детерминировано;
- атомарность блока исключает частично применённые блоки;
- сохранение количества средств: сумма балансов растёт ровно на награду за блок.

Минусы:
- клонирование состояния на каждый блок стоит `O(число аккаунтов)`. Для учебного проекта
  приемлемо, для реальной сети нужен журнал отмены или персистентные структуры;
- отклонение от ТЗ (аккаунт вместо числа). Исправлено в самом ТЗ;
- строгий порядок nonce: потерянная транзакция блокирует все последующие от того же
  отправителя. Пула транзакций в J1 нет, поэтому не проблема;
- нулевые и самоадресные переводы отвергаются, что строже, чем в некоторых реальных сетях.

## Рассмотренные альтернативы

1. **`BTreeMap<String, u64>` из ТЗ и отдельная таблица nonce.** Две структуры нужно
   поддерживать согласованно, удобнее одна запись на адрес.
2. **UTXO-модель (как в Bitcoin).** Защита от replay получается из того, что вход тратится
   один раз, но требует входов и выходов в транзакции. Это другая структура транзакции,
   отвергнуто в пользу счетной модели из ТЗ.
3. **Журнал отмены вместо клонирования.** Эффективнее по памяти, но заметно сложнее.
   Откладывается до задач с реорганизацией цепи (J4).
4. **Разрешить `amount = 0` и `from == to`.** Требует отдельного решения, как вести себя
   в этих случаях, и допускает «мусорные» транзакции. Отвергнуто.

## Тесты, фиксирующие решение

- Пустое состояние: баланс 0 и `next_nonce` 0 для любого адреса.
- Coinbase начисляет 50, последующие блоки накапливают.
- Перевод: баланс отправителя убывает, получателя растёт, `next_nonce` отправителя 1, получателя 0.
- Недостаточно средств, неверный nonce (меньше, больше, повтор), неизвестный отправитель,
  нулевая сумма, перевод самому себе: каждый случай даёт свою ошибку и не меняет состояние.
- Переполнение баланса получателя и `next_nonce` (`u64::MAX`).
- Блок: coinbase и переводы применяются по порядку; трата полученного в том же блоке
  работает; nonce 0 и 1 подряд проходят, 0 и 0 нет.
- Блок без coinbase в начале, с двумя coinbase, с неверной наградой или неверным `nonce`
  coinbase, пустой блок: ошибки.
- Атомарность: валидная coinbase и затем невалидная транзакция оставляют состояние прежним.
- Сохранение количества средств: сумма балансов после блока равна сумме до блока плюс 50.
