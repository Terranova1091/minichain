# ADR 0006: Цепочка блоков и правила её валидации

- Статус: принято
- Дата: 2026-11-07
- Связано: ADR 0002 (PoW), ADR 0003 (пересчёт сложности, дополнен этим ADR),
  ADR 0004 (генезис), ADR 0005 (состояние)

## Контекст

Блок можно проверить по частям (Merkle-корень, PoW, применение к состоянию), но
консенсус определяется правилами **добавления блока в цепь**. Нужна сущность `Chain`,
которая хранит блоки и производное состояние и отвечает на два вопроса:

1. можно ли добавить этот блок в конец цепи (`add_block`);
2. корректна ли цепь целиком (`validate`, `from_blocks`). Это нужно при загрузке
   из файла: файлу доверять нельзя, цепь проверяется заново с генезиса, и любой
   подменённый байт должен быть обнаружен.

Правила для обоих вопросов должны быть одними и теми же и существовать в одном месте.

## Решение

### 1. Единая проверка блока

Функция `Chain::validate_block(&self, block, now) -> Result<State, BlockValidationError>`
проверяет блок относительно хвоста цепи и **не изменяет цепь**. Она возвращает состояние
после применения блока, чтобы `add_block` мог принять его без повторных вычислений.

`add_block` вызывает `validate_block` и при успехе дописывает блок и заменяет состояние;
при ошибке цепь остаётся прежней. `Chain::from_blocks` строит цепь из генезиса и
добавляет остальные блоки через `add_block`. `Chain::validate` реализуется через
`from_blocks`, так что второй копии правил нет.

### 2. Проверки блока

Проверки идут от дешёвых к дорогим, первая сработавшая ошибка возвращается сразу.

| № | Проверка                                                     | Ошибка                              |
|---|--------------------------------------------------------------|-------------------------------------|
| 1 | `version == BLOCK_VERSION`                                   | `WrongVersion { expected, got }`    |
| 2 | `height == tip.height + 1`                                   | `WrongHeight { expected, got }`     |
| 3 | `prev_hash == tip.hash()`                                    | `PrevHashMismatch`                  |
| 4 | `bits == expected_bits(blocks)`                              | `WrongBits { expected, got }`       |
| 5 | Merkle-корень верен, список транзакций не пуст               | `Block(BlockError)`                 |
| 6 | PoW выполнен: `header.meets_target()`                        | `InsufficientWork`                  |
| 7 | `timestamp > median_time_past(blocks)`                       | `TimestampTooOld { median, got }`   |
| 8 | `timestamp <= now + MAX_FUTURE_SECS`                         | `TimestampInFuture { limit, got }`  |
| 9 | транзакции валидны по состоянию (`State::apply_block`)       | `State(StateError)`                 |

Хэш блока (для проверок 3 и 6) всегда считается узлом из заголовка и никогда не берётся
из полученных данных.

Проверка 4 стоит раньше PoW: блок с неверным `bits` не стоит пересчитывать хэш.
Применение к состоянию последнее, потому что оно самое дорогое (клонирование состояния).

### 3. Генезис

Генезис не проходит проверки 1–4 и 7–8 как обычный блок. Он валиден, если равен
`genesis(bits)` с `bits` из собственного заголовка (ADR 0004). Если `genesis(bits)`
возвращает ошибку или результат отличается от блока из цепи, ошибка `InvalidGenesis`.

### 4. Время

- `now` передаётся параметром (`u64`, секунды Unix), а не берётся из `SystemTime`.
  Системные часы читаются только в CLI. Благодаря этому правила детерминированы и
  тестируются без зависимости от часов.
- `MAX_FUTURE_SECS = 120`. Метка, равная `now + 120`, допустима, `now + 121` нет.
- Метка строго больше медианы: равная медиане не допускается.
- Историческая цепь при `validate` проверяется текущим `now`. Правило «не в будущем»
  от этого только мягче, поэтому ранее принятые блоки не становятся недействительными.

### 5. Медиана времени (median time past)

`median_time_past(blocks)` принимает блоки **до** проверяемого. Берутся последние
`min(11, blocks.len())` блоков **по позиции**, их метки копируются в вектор,
сортируются, и возвращается элемент с индексом `len / 2` (для чётного числа это верхняя
медиана). Для первого блока после генезиса медиана равна метке генезиса.

Число 11 (`MEDIAN_WINDOW`) соответствует ТЗ. Выбор верхней медианы для чётного числа
записан явно, потому что от него зависит консенсус.

### 6. Ожидаемый `bits`

`expected_bits(blocks) -> Option<u32>` принимает блоки до нового; высота нового блока
`h = blocks.len()`. Для пустого среза возвращает `None`.

- если `h` не высота пересчёта (`!is_retarget_height(h)`), `bits` равно `bits` последнего блока;
- иначе `next_bits(prev.bits, actual, expected)` по окну из следующего пункта.

### 7. Дополнение к ADR 0003: начало окна пересчёта

ADR 0003 определял окно как блоки `h-10 … h-1`. Для первого пересчёта (`h = 10`) оно включало
генезис, метка которого фиксирована константой (`GENESIS_TIMESTAMP`, 2023 год), тогда как
реальные блоки майнятся в текущее время. Разность `timestamp(9) - timestamp(0)` составила бы
годы, и сложность на высоте 10 всегда падала бы на 2 бита независимо от темпа блоков 1…9.

Правило уточняется: окно не начинается раньше блока 1.

- `h = 10`: окно блоков 1…9, 8 интервалов, `expected = 80`;
- `h = 20` и далее: окно из 10 блоков, 9 интервалов, `expected = 90`.

Функция `next_bits` не меняется (она принимает `expected_secs`). Статус ADR 0003 следует
дополнить строкой «Уточнён ADR 0006, п. 7».

### 8. Состояние

`Chain` хранит `blocks: Vec<Block>` и `state: State`. Состояние производное и не
сохраняется в файл. При `validate` и `from_blocks` оно вычисляется заново от пустого.
Блоки в `add_block` применяются к клону состояния (ADR 0005), поэтому при ошибке
в цепи ничего не меняется.

### 9. Ошибки

`BlockValidationError`: `EmptyChain`, `WrongVersion`, `WrongHeight`, `PrevHashMismatch`,
`WrongBits`, `Block(BlockError)`, `InsufficientWork`, `TimestampTooOld`,
`TimestampInFuture`, `State(StateError)`.

`ChainError`: `EmptyChain`, `InvalidGenesis`, `InvalidBlock { height, reason }`.

Поле `height` в `InvalidBlock` равно **позиции блока в цепи** (индексу, куда он встал бы),
а не значению из заголовка: заголовок блока может содержать неверную высоту.
Это даёт понятное сообщение об ошибке с номером повреждённого блока, как требует ТЗ.

Все ошибки реализуют `Debug, Clone, PartialEq, Eq`, вложенные ошибки пробрасываются через `From`.
В библиотечном коде нет `unwrap`, `expect` и индексации, которая может паниковать:
обращения к блокам идут через `.get()`, `.first()`, `.last()`.

## Последствия

Плюсы:
- единый источник правил для добавления блока и для проверки всей цепи;
- любая подмена в старом блоке обнаруживается с указанием высоты: изменение транзакции
  ломает Merkle-корень, изменение заголовка ломает PoW или `prev_hash` следующего блока;
- проверки детерминированы и не зависят от системных часов;
- добавление блока атомарно.

Минусы:
- `validate` перепроигрывает всю цепь за `O(n)` блоков и клонирует состояние на каждом блоке,
  что `O(n * число аккаунтов)`. Для учебной цепи приемлемо;
- каждый `validate` заново пересчитывает PoW для всех блоков (один хэш на блок, это дёшево);
- правило окна для высоты 10 отличается от всех последующих (8 интервалов вместо 9);
  это осознанное исключение, зафиксированное тестом;
- манипуляция метками времени в пределах правил возможна: майнер может сдвигать метку
  в диапазоне `(median, now + 120]`. Медиана ограничивает влияние одной метки.

## Рассмотренные альтернативы

1. **Отдельная функция `validate` с собственной копией правил.** Правила разойдутся со временем.
   Отвергнуто в пользу `from_blocks` поверх `add_block`.
2. **Читать системные часы внутри `validate_block`.** Тесты становятся нестабильными
   и недетерминированными. Отвергнуто.
3. **Оставить генезис в окне первого пересчёта (ADR 0003 без правки).** Сложность на высоте 10
   стабильно падает на 2 бита из-за разрыва меток. Отвергнуто.
4. **Сделать метку генезиса «текущим временем».** Генезис перестаёт быть детерминированным
   (ADR 0004). Отвергнуто.
5. **Хранить состояние в файле.** Дублирует данные и создаёт ещё одну вещь, которую нужно
   проверять при загрузке. Отвергнуто: состояние вычисляется из блоков.
6. **Простая медиана без верхней и нижней границы для чётного числа.** Неоднозначно для
   консенсуса. Отвергнуто в пользу фиксированного правила `len / 2`.

## Тесты, фиксирующие решение

- Цепь из 25 блоков с корректными метками проходит `validate`; блоки на высотах 10 и 20
  используют пересчитанные `bits`.
- Каждое правило из таблицы нарушается отдельно и даёт свою ошибку с высотой блока.
- Подмена байта в старом блоке: сумма транзакции в блоке 3 даёт ошибку Merkle на высоте 3;
  изменение `nonce` даёт `InsufficientWork` на высоте 3 или `PrevHashMismatch` на высоте 4.
- Подмена генезиса даёт `InvalidGenesis`.
- Граница метки: `median` не проходит, `median + 1` проходит; `now + 120` проходит,
  `now + 121` нет.
- Пересчёт на высоте 10: быстрые блоки дают +2, медленные −2, блок с неверными `bits` отвергается.
  Метка генезиса на результат не влияет (окно 1…9, `expected = 80`).
- `add_block` атомарен: после ошибки блоки и состояние равны прежним.
- `median_time_past`: 1, 2, 11 и 12 блоков, несортированные метки, учитываются только последние 11.
- `expected_bits` для высот 1…9, 10, 11, 20 и пустого среза (`None`).
