# ADR 0007: Хранение цепи в JSON-файле с полной валидацией при загрузке

- Статус: принято
- Дата: 2026-11-14
- Связано: ADR 0004 (генезис), ADR 0005 (состояние), ADR 0006 (валидация цепи)

## Контекст

Цепь живёт в памяти и теряется при перезапуске. Нужно сохранять её в один файл и
загружать обратно (ТЗ: `save(path)` и `load(path)` через `serde_json`).

Главное требование проекта J1: цепь обнаруживает любой подменённый байт. Файл
доступен для редактирования любому, поэтому при загрузке ему нельзя доверять, а повреждённый
файл должен давать понятную ошибку с высотой блока.

JSON допустим в проекте только для файла хранения. Хэши всегда считаются от канонических
байтов (ADR 0001, формат заголовка и транзакции), а не от JSON: порядок ключей и пробелы
не должны влиять на консенсус.

## Решение

### 1. Что хранится
`ChainFile { format_version: u32, blocks: Vec<Block> }`

- Только блоки. **Состояние (балансы, nonce) не хранится**: оно производное и вычисляется
  при загрузке (ADR 0005, ADR 0006). Хранить его значило бы добавить ещё одну подделываемую
  сущность, которую пришлось бы проверять.
- **Хэши блоков не хранятся**: они вычисляются из заголовков. Поля `prev_hash` и
  `merkle_root` входят в заголовок и хранятся как его часть.
- Начальная сложность (`bits` генезиса) определяется заголовком первого блока (ADR 0004).
- `format_version = 1`. Файл с другой версией отвергается ошибкой `UnsupportedVersion`.

### 2. Формат файла

- JSON, `serde_json::to_string_pretty` (с отступами), в кодировке UTF-8.
- `Hash` записывается строкой из 64 hex-символов в нижнем регистре, а не массивом из 32 чисел.
  При чтении используется `Hash::from_str`; регистр принимается так, как его принимает
  `from_str`. При следующем сохранении запись всегда нормализуется к нижнему регистру.
  Это безопасно: хэш определяется байтами, а не их текстовой записью.
- Числа `u64` и `u32` записываются как обычные JSON-числа (`serde_json` поддерживает полный
  диапазон `u64`).
- Структуры помечены `#[serde(deny_unknown_fields)]`: неожиданное поле в файле является
  ошибкой, а не молча игнорируется. Это ловит опечатки и грубые подмены.
- Вывод детерминирован: одна и та же цепь всегда сериализуется в одни и те же байты
  (порядок полей задан структурами, а не картами).

### 3. Загрузка

`Chain::load(path, now)`:

1. прочитать файл целиком (`fs::read_to_string`);
2. разобрать в `ChainFile` (`serde_json::from_str`);
3. проверить `format_version`;
4. `Chain::from_blocks(file.blocks, now)`.

Шаг 4 выполняет те же проверки, что и `add_block` для каждого блока (ADR 0006), включая
проверку генезиса, Merkle-корня, PoW, `bits`, меток времени и применения к состоянию.
Отдельной «упрощённой» проверки при загрузке нет. Ошибка содержит высоту блока:
`StorageError::Chain(ChainError::InvalidBlock { height, reason })`.

Время `now` передаётся параметром (как в `validate`), системные часы читаются только в CLI.

### 4. Сохранение

`Chain::save(&self, path)` пишет **атомарно**:

1. сериализовать цепь в строку;
2. записать во временный файл в той же папке: имя целевого файла с суффиксом `.tmp`;
3. вызвать `sync_all` для временного файла (данные доходят до диска до переименования);
4. `fs::rename(tmp, path)`.

Если процесс завершится посреди записи, целевой файл остаётся прежним и целым, а
временный файл не принимается за цепь. При ошибке записи временный файл по возможности
удаляется.

### 5. Ошибки
`StorageError:`
`Io(std::io::Error) #[from]`
`Json(serde_json::Error) #[from]`
`UnsupportedVersion { found, expected }`
`Chain(ChainError) #[from]`
_
`StorageError` не реализует `PartialEq` (из-за `std::io::Error`), в тестах проверки идут
через `matches!`. Из-за этого `Io` не входит в `ChainError`: тот сравнивается через `==`
в тестах валидации.

## Последствия

Плюсы:
- любая подмена в файле (сумма, nonce, метка времени, генезис) обнаруживается при загрузке
  с указанием высоты блока;
- единый источник правил: загрузка использует `from_blocks`, а не собственную проверку;
- файл читается человеком и редактируется в тестах без специальных инструментов;
- атомарная запись защищает от частично записанного файла.

Минусы:
- файл хранит только блоки, поэтому загрузка тратит время на перепроигрывание всей цепи
  (`O(n)` блоков, один хэш на блок плюс применение транзакций). Для учебной цепи
  приемлемо;
- файл читается целиком в память, ограничения размера нет. Огромный файл приведёт к большому
  расходу памяти;
- блокировки файла нет: два процесса, пишущих одновременно, не координируются. В J1 узел
  один, это известное ограничение;
- JSON избыточен по размеру (хэши в hex, отступы). Эффективность в проекте не цель.

## Рассмотренные альтернативы

1. **Хранить состояние вместе с блоками.** Ускоряет загрузку, но состояние можно подделать
   независимо от блоков, и его пришлось бы сверять с блоками, то есть пересчитывать всё
   равно. Отвергнуто.
2. **Хранить хэши блоков в файле.** Дублирует вычисляемые значения и добавляет ещё одну
   проверку. Отвергнуто.
3. **Бинарный формат на основе канонической кодировки.** Компактнее и ближе к реальным
   узлам, но ТЗ требует `serde_json`, а читаемость файла полезна для тестов. Отвергнуто
   для J1.
4. **`Hash` как массив из 32 чисел.** Принимается serde по умолчанию, но нечитаем и неудобен
   для ручных подмен в тестах. Отвергнуто.
5. **Запись напрямую в целевой файл.** Сбой посреди записи оставляет повреждённый файл
   на месте целой цепи. Отвергнуто в пользу временного файла и `rename`.
6. **Отдельная «лёгкая» проверка при загрузке.** Правила разойдутся с `add_block`.
   Отвергнуто.

## Тесты, фиксирующие решение

- Круговой проход: `save` и `load` возвращают цепь, равную исходной (блоки и состояние);
  `validate` проходит.
- Подмена суммы транзакции в блоке 3 редактированием JSON даёт
  `Chain(InvalidBlock { height: 3, reason: Block(MerkleRootMismatch) })`.
- Подмена `nonce` или метки времени в заголовке даёт `InvalidBlock` на этом блоке или на следующем.
- Подмена генезиса даёт `Chain(InvalidGenesis)`.
- Пустой, обрезанный и не-JSON файлы дают `Json`.
- `format_version` не равный 1 даёт `UnsupportedVersion`.
- Лишнее поле в любом объекте даёт `Json`.
- Некорректный hex в хэше (длина, символы) даёт `Json`.
- Пустой список блоков даёт `Chain(EmptyChain)`.
- Отсутствующий файл даёт `Io` с `NotFound`; запись в несуществующую папку даёт `Io` и не создаёт файлов.
- После успешного `save` временного файла нет; существующий файл заменяется целиком.
- Два `save` одной цепи дают побайтово одинаковые файлы.
