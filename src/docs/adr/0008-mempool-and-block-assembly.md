# ADR 0008: Очередь транзакций, сборка блока и порядок сохранения

- **Статус:** принято
- **Дата:** 2026-11-17
- **Связано:** ADR 0005 (состояние), ADR 0006 (валидация цепи), ADR 0007 (хранение)

## Контекст

До этого шага цепь можно было строить только из кода: у библиотеки не было места, где живут транзакции, ожидающие включения в блок, и не было функции, которая собирает блок из них. Для консольного интерфейса (`send`, `mine`) нужно решить:

1. где хранятся неподтверждённые транзакции и в каком формате;
2. по каким правилам транзакция принимается в очередь;
3. как блок собирается из очереди и какую метку времени получает;
4. в каком порядке сохраняются файлы, чтобы сбой между записями ничего не ломал;
5. где в программе читаются системные часы.

## Решение

### 1. Очередь хранится отдельным файлом

Очередь (mempool) лежит в `pending.json` рядом с `chain.json`:

```json
{ "format_version": 1, "transactions": [ ... ] }
```

Правила формата те же, что в ADR 0007: `deny_unknown_fields`, двухэтапная проверка версии (сначала только `format_version`, затем полная структура), атомарная запись (tmp, `sync_all`, `rename`). Версия формата очереди независима от версии формата цепи. Отсутствие файла означает пустую очередь и не является ошибкой. Запись пустой очереди это файл с пустым списком, файл не удаляется.

Содержимое очереди при загрузке **не валидируется**: состояния под рукой нет. Валидация выполняется отдельным шагом (`revalidate`, п. 3).

### 2. Транзакция принимается по проекции состояния

Новая транзакция проверяется не против текущего состояния цепи, а против состояния, **спроецированного** применением всех уже стоящих в очереди транзакций в порядке очереди. Проверка делегируется правилам `State` (nonce, баланс, переполнение), собственной арифметики в очереди нет.

Следствия:

- очередь принимает только то, что блок сможет применить в том же порядке;
- входящие переводы в очереди учитываются (получил, потом потратил);
- nonce новой транзакции равен `next_nonce` отправителя в проекции;
- транзакции с пустым `from` (награда) в очередь не принимаются: их создаёт только сборка блока.

### 3. `revalidate` приводит очередь в соответствие состоянию

`revalidate(&mut self, &State) -> Vec<Transaction>` строит очередь заново: идёт по старой очереди в порядке добавления и добавляет каждую транзакцию через общую проверку (п. 2). Принятые остаются, отвергнутые возвращаются вызывающему коду для отчёта пользователю.

Очередь считается кэшем намерений, а не источником истины. Поэтому `revalidate` вызывается:

- сразу после загрузки очереди в командах, которые её меняют (`send`, `mine`);
- после добавления блока в цепь (убирает включённое и ставшее невалидным).

Метод не знает о блоках: включённые транзакции отваливаются сами, потому что их nonce уже использован.

### 4. Сборка блока: `Chain::build_block`

```rust
fn build_block(&self, miner: &str, pending: &[Transaction], now: u64)
    -> Result<BuiltBlock, BuildError>
```

- Функция **чистая**: не читает часы и файлы, не меняет цепь, не майнит. `now` приходит параметром. Майнинг и `add_block` выполняет вызывающий код.
- Первой идёт транзакция-награда: пустой `from`, `COINBASE_REWARD`, `nonce` равен высоте блока.
- Блок только с наградой проверяется отдельно: ошибка здесь означает, что отвергнут адрес майнера (`BuildError::Coinbase`).
- Транзакции очереди добавляются по одной. Применимость проверяется пробным прогоном блока «уже включённое плюс кандидат» через `State::apply_block` на копии состояния, то есть теми же правилами, которые потом применит валидация. Применимые включаются, остальные возвращаются в `skipped`. Порядок очереди сохраняется, поэтому цепочка зависимых транзакций пропускается целиком, если пропущено её начало.
- Параметры блока (высота, `bits`, предыдущий хэш) вычисляются так же, как их проверяет `validate_block`; `bits` берётся через `expected_bits`, поэтому пересчёт сложности учитывается автоматически.

### 5. Метка времени нового блока

```
timestamp = max(now, median_time_past + 1)
```

Если `timestamp > now + MAX_FUTURE_SECS`, блок не собирается: `BuildError::ClockBehind { now, min }`. Иначе сеть (то есть `validate_block`) отвергла бы собственный блок.

### 6. Порядок сохранения в `mine`

1. загрузить цепь и очередь;
2. `revalidate` очереди (чистка перед работой);
3. `build_block`, `mine`, `add_block`;
4. **сохранить цепь**;
5. `revalidate` очереди на новом состоянии;
6. **сохранить очередь**.

Цепь сохраняется раньше очереди. Если процесс прервётся между шагами 4 и 6, в `pending.json` останутся уже включённые транзакции; следующая команда отбросит их в шаге 2. Обратный порядок мог бы безвозвратно потерять транзакции.

### 7. Консольный интерфейс

- Системные часы читаются **ровно в одном месте**, в `main`. Значение передаётся в `cli::run` и дальше параметром `now`.
- `send` вычисляет `nonce` сам (nonce из состояния плюс число транзакций отправителя в очереди), пользователь его не указывает. Если транзакция отвергнута, очередь не сохраняется.
- `init` не перезаписывает существующую цепь.
- Коды возврата: `0` при успехе, `1` при ошибке; сообщение об ошибке уходит в stderr, паник в `cli.rs` нет.
- Функция `run` принимает время и поток вывода параметрами, поэтому тестируется без запуска процесса.

## Рассмотренные альтернативы

| Альтернатива | Почему отвергнута |
|---|---|
| Хранить очередь внутри `chain.json` | Смешивает подтверждённое и неподтверждённое; каждый `send` перезаписывал бы всю цепь; нарушается правило «состояние файла цепи определяется только блоками». |
| Очередь только в памяти | CLI состоит из отдельных запусков, между ними очередь пропала бы. |
| Проверка по формуле `balance >= pending_sum + amount` | Не учитывает входящие переводы в очереди и дублирует правила `State`; очередь и блок могли бы разойтись. |
| Проверка только против подтверждённого состояния | Принимает транзакции, которые блок отвергнет (двойная трата внутри очереди). |
| Удалять из очереди «включённые» по идентификатору | Требует идентификаторов транзакций и отдельной логики; `revalidate` решает задачу без неё и заодно чистит всё остальное. |
| Сохранять очередь раньше цепи | При сбое транзакции теряются безвозвратно. |
| Читать время внутри библиотеки | Детерминизм и тестируемость пропадают; прежние решения (ADR 0006) передают `now` параметром. |
| Применять транзакцию к `State` отдельным методом при сборке | Быстрее, но дублирует правила применения; выбран пробный прогон блока, чтобы источник истины был один. |

## Последствия

**Плюсы**

- Очередь и блок используют одни и те же правила применения: всё, что принято в очередь, применится в блоке в том же порядке.
- Самовосстановление: любое рассогласование файлов после сбоя исправляется при следующем запуске.
- `build_block` чистая и тестируется при малой сложности за миллисекунды.
- Один источник времени и явная передача `now` делают поведение воспроизводимым в тестах.

**Минусы и ограничения**

- Пробный прогон блока на каждую транзакцию даёт квадратичную сложность сборки; приемлемо для учебного объёма.
- Размер очереди и число транзакций в блоке не ограничены; комиссий и приоритетов нет, порядок строго по времени добавления.
- Нет блокировки файлов: два параллельных запуска над одним каталогом могут потерять одну из записей (атомарность защищает от повреждения файла, но не от гонки).
- Транзакция, отвергнутая при сборке из-за временной причины, после следующего `revalidate` будет отброшена окончательно (повторить её придётся командой `send`).
- Счётчик `pending` в `show` берётся из файла и может включать устаревшие записи.

## Что нужно проверить тестами

- Очередь: отказ для награды, неверного nonce и перерасхода; принятие депозита с последующей тратой; цепочка из нескольких транзакций одного отправителя; `revalidate` после включения транзакции в блок и после пропажи зависимости.
- Файл очереди: отсутствие файла, roundtrip, версии, лишние и недостающие поля, атомарность записи.
- `build_block`: пустая очередь, порядок, `skipped`, зависимые транзакции, граница `ClockBehind` (`median + 1 == now + 120` проходит, `now + 121` нет), пустой адрес майнера, неизменность цепи.
- CLI: сквозной сценарий, повторный `init`, `send` без монет, два `send` и один `mine`, повреждённая цепь и `verify`.
